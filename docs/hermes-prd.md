# Hermes 家庭助手 PRD

> 状态：需求持续整理；Spotify 官方插件、米家 CLI＋skill 与 Windows（AgentDock）基础接入已完成。米家只读链路已验收；Windows 控制、米家控制 / 播报等用户故事仍需实机验收。最后更新：2026-10-19。
> 适用部署：Oracle 上的 Hermes，profile `muse-home`。
> 本文独立管理云端助手的需求与验收，不再沿用音箱 bridge 的迁移阶段编号。音箱只是交互入口之一，网页聊天同样需要具备这些能力。

## 1. 执行摘要

### 问题

现有 Hermes 能调用米家与 Spotify，但暴露的能力不足，个人歌单和歌曲身份经常匹配错误，多步工具调用容易耗尽轮数；工具故障还会被记成用户偏好。需要让助手理解自然描述、读取真实个人数据、完成操作并如实反馈。

### 方案

保留现有 Hermes，米家使用上游 mijiaAPI CLI＋skill，Spotify 使用 Hermes 官方插件；旧自定义米家服务保留供回退。以现成能力、外部事实查询和可更新的个人记忆支持泛化；提示词规定方法和行为边界，不堆积设备表、歌曲、动漫或个人同义词对照表。主动提醒直接走米家云端接口。定时使用 Hermes cron，习惯使用 Hermes 记忆；每周记忆核对由 Grok Bot 负责。

### 成功标准

以下沿用原计划的验收目标，属于待评测的目标，不代表当前已达到：

| 指标 | 目标与口径 |
|---|---|
| 米家任务完成率 | 固定评测集 ≥ 95%，包含设备选择、动作、参数和结果回报 |
| Spotify 任务完成率 | 固定评测集 ≥ 90%，并单独报告新描述、新歌单叫法的泛化结果 |
| 虚报成功 | 评测中 0 次；区分请求被接受、执行失败和状态已核实 |
| 记忆正确性 | 验收中不把工具故障、公共同名歌单或未确认推断写为用户事实；明确纠正后新会话使用更新值 |
| 步数与延迟 | 改动前后记录工具步数、失败重试、首个有效反馈和任务完成时间；当前未确定绝对延迟门槛，不虚设达标结果 |

推荐是否合口味由用户反馈判断；读取了收藏、候选真实存在和理由有据是必要条件，不能以模型自评代替用户评价。

## 2. 用户体验与功能

### 用户与入口

面向同一位用户的家庭助手：在家可以通过缪斯音箱发出请求，也可以在 Hermes 网页聊天中控制米家、整理音乐和安排任务。云端米家控制与提醒不依赖 Windows 开机。Spotify 播放依赖在线的 Spotify Connect 设备，当前默认设备为用户的 Windows 电脑。

### Spotify 用户故事

用户已确认自己是 Spotify Premium 会员。以下例子是验收场景，不应写成只支持这些名字的运行时规则。

| 编号 | 用户说法 | 预期行为 |
|---|---|---|
| SP1 | “我觉得《钢之炼金术士》新版的第二首 ED 很好听，你能帮我收藏吗？” | 查清作品版本、ED 顺序、歌名与演唱者，在 Spotify 匹配正确录音，加入用户自己的 ACG 歌单；已有时不重复添加 |
| SP2 | “放我的 xx 歌单” | 优先找账号内真实的个人歌单，默认随机播放；明确要求按顺序时覆盖默认偏好 |
| SP3 | “放二次元歌单” / “来点摇滚” | 没有同名个人歌单时，结合真实歌单推断 ACG / rock 等候选，询问“你是指这个吗”；用户确认后执行，并由 Hermes 原生记忆整理叫法偏好，后续请求能复用 |
| SP4 | “根据我的品味推荐一首歌” | 实际读取收藏和歌单后选歌，按权限及需要补近期播放、偏好排行；说明与已知口味的具体联系 |
| SP5 | 换动画、换 OP / ED、换译名、换歌单叫法，或追问“换一首”“把这首也加进去” | 结合真实数据与上下文处理未见过的表达；仍有关键歧义时只问必要的问题 |

验收细则：

- **歌曲身份**：不能直接收藏搜索结果第一条。需要区分原唱、翻唱、伴奏、现场和 TV size / 完整版；默认优先原唱的正式完整录音，这是待验证的产品默认值。若版本影响意图且无法唯一确定，则询问。没有版权时如实说明，不偷偷用翻唱替代。
- **收藏目的地**：SP1 已明确希望归入 ACG，不自动再加入“喜欢的歌曲”。其他请求结合当前对话、歌单语义和用户已确认偏好确定目标；依据不足时不擅自分配。
- **个人歌单**：读取全部分页，区分自己的、可编辑的和仅关注的歌单。按真实 playlist ID 操作；歌单改名后可继续追踪，删除或失去访问权时重新查找。
- **随机播放**：设置并核对随机状态，开播位置也应避免每次固定第一首；明确的顺序播放指令优先。核对实际播放设备和歌单；曲目短时间内未更新时不立即把异步延迟当失败，也不未经核实就声称已经播对。
- **语义理解与首次确认**：先找个人歌单中的准确匹配；没有同名歌单时，结合歌单名、描述、必要的曲目样本和上下文推断候选，例如询问“你是指 ACG 这个歌单吗”。等用户确认后再执行。“二次元 → ACG”“摇滚 → rock”只是需求示例，不是已经确认的个人叫法，不预先写入记忆、SOUL.md 或代码。
- **原生记忆学习**：首次候选经用户确认后，使用 Hermes 已有记忆能力整理个人叫法；后续能直接复用，用户纠正时更新。先验证现有行为，只有原生能力在评测中实际不足时才针对问题调整通用说明；不新增别名数据库、同义词规则、独立学习模块或专门的记忆写入封装。歌单默认随机播放则是用户明确提出的产品要求，与上述尚待确认的叫法分开处理。
- **推荐依据**：先读取收藏 / 个人歌单，采用有限样本和缓存减少重复读取。默认优先推荐收藏之外、本会话未推荐过且在 Spotify 可用的曲目。推荐理由应对应实际证据；数据不足或仅能核对部分收藏时明确说明。
- **执行确认**：添加前去重，使用真实 URI；执行结果和必要的读回检查由通用工具或工作流保证，不让模型每次重新拼接。遇到超时等不确定结果时先查当前状态，再决定是否重试，避免重复添加。

### 米家、主动提醒与记忆用户故事

保留旧方案的故事编号，便于追踪已有需求。

| 编号 | 场景 | 预期与验收 |
|---|---|---|
| S2 | “我今晚想洗澡” | 读取记忆中的入睡时间、洗澡与加热习惯，安排热水器提前开启并说清时间；缺少必要习惯或加热参数时询问，不编造 |
| S4 | “打开热水器 / 电热毯” | 执行后按需安排提醒；“洗完了 / 关掉”关闭设备并取消对应提醒。防忘关不由 Hermes 常驻服务承担：电热毯由用户在米家设定时开关；热水器通电时由 Hermes 同时建一次性定时关闭任务（cron），手动关闭时取消 |
| S5 | “播放 Spotify / 打开 xx 软件” | Spotify 播放使用官方插件；启动 / 关闭 Windows 程序、音量、锁屏等经 AgentDock 与 `windows-control` skill 执行 |
| S6 | 不在家，从网页说“把空调关了” | 直接调用云端米家工具，Windows 关机时仍可执行 |
| S7 | 长对话或新会话中控制设备 | 设备知识和稳定习惯仍有效，不依赖早先对话是否留在上下文中 |
| H1 | “屋里几度 / 门关了吗” | 读取真实传感器；全屋状态查询争取一次工具调用返回，保留采样时间和缺失状态 |
| H2 | “记住我工作日十一点半睡”后，新会话说“我今晚想洗澡” | 使用已确认习惯，不重复询问；“你记错了 / 忘掉……”能替换或删除对应记忆 |
| H3 | 定时提醒到点 | cron 实际调用米家云端播报工具，Windows 关机时也能播；明确区分云端接受请求与确认实际播完 |
| H4 | 新增 / 移除 / 改名设备后说“更新一下设备列表” | 从米家云端刷新当前家庭的设备和场景，报告变化，新设备可查询与操作，无需改代码或提示词；只下线的设备保留身份并标离线 |
| H5 | “这个插座现在接的是电热毯，以后叫它电热毯” | 用户确认的叫法与用途由原生记忆保存；不能因为记了用途就声称该设备已有自动关闭保护 |

通用体验：

- “亮一点 / 暗一点”采用可解释的相对调整；原方案默认 ±20%，“暖一点 / 白一点”调整色温。实际属性和单位以设备规格为准。
- “我要睡了”“出门了 / 回来了”等场景通过真实场景清单理解；“好冷 / 好热”仅表达感受时先确认是否需要操作。
- 一句话有多个动作时，在同一任务中完成并分别核实；部分失败不能概括为全部成功。
- 普通成功回报尽量一句话；失败只说明一次原因和可行的下一步。必要澄清应能区分候选，避免反复确认明确指令。
- 工具等待提示“稍等 / 我查一下”在音箱入口已有实现，云端工具进度需要与入口配合，避免两边重复播提示。

### 记忆要求与分工

| 信息 | 存放与更新方式 |
|---|---|
| 设备 ID、家庭 / 房间、型号、能力、在线状态、场景 | 米家云端发现并维护带更新时间的设备目录；启动预热，支持主动刷新；属性和动作按设备规格读取。SOUL.md 只写查询和使用方法，避免重复抄设备表 |
| 明确的禁用设备 / 场景 | 独立的家规配置，由 CLI 启动校验执行；设备发现不覆盖用户已确认的规则，不依赖模型背诵提示词 |
| 稳定偏好、个人叫法 | 复用 Hermes 原生用户记忆；用户明确表达或确认后整理保存。PRD 中的例子不构成已确认的个人叫法，不预填 |
| 通用操作方法 | skill / 工具说明；不依赖一次性会话内容 |
| 工具缺陷、接口失败、系统故障 | 运维记录，不写成用户偏好 |
| 每周记忆核对 | 用户通过 Grok Bot 完成；Hermes 不建立周期核对或自动清理任务 |

记忆写入还需遵守：

- 不从一次请求就推断长期偏好。重复出现的偏好可提出确认，不能把“多次出现”当成事实真实性的替代。
- 歌名、艺人名和歌单身份以工具核实及用户确认的信息为准；用户没纠正不能单独作为拥有某个歌单或喜欢某艺人的证明。
- 用户纠正时替换旧值，不保留互相矛盾的两条有效偏好；支持查询、纠正、遗忘。
- 一次性清理旧的错误“我的摇滚”记忆；Spotify 功能修好后移除不再成立的两条工具缺陷笔记。执行前定位具体条目，避免误删其他偏好。

### 范围边界

当前范围包括云端米家、Spotify、提醒、记忆、模型行为、Windows 控制及其验收。Windows 控制经 AgentDock 接入，电脑关机或离线时不可用；它不是云端米家与提醒功能的前提。

音箱麦克风、KWS、AEC、灯效、TTS 和连续对话状态机归 bridge 维护；本 PRD 不重新设计这些功能。不引入 Home Assistant，不重造 Hermes 的记忆和 cron，也不为主动播报新增一条公网 bridge 通路。

## 3. AI 系统要求

### 通用决策流程

1. 解析意图与当前对话指代，识别还缺少哪些事实或个人信息。
2. 从工具读取真实状态、个人数据及已确认记忆；涉及作品知识时按需要搜索可靠资料。
3. 选择操作对象和参数；只有关键歧义仍无法消除时询问。
4. 使用真实设备 / 歌单 ID 或曲目 URI 执行，核实结果并处理部分失败。
5. 简短回报；仅在符合记忆写入规则时更新稳定偏好。

工具负责分页、去重、标识规范化、权限、固定动作、结果读回和必要缓存；模型负责理解自然描述、选择工具、综合事实和提出有针对性的澄清。先使用官方工具和通用工作流，确有缺口再补封装。

### 工具与数据需求

| 能力 | 首选实现 | 待核对事项 |
|---|---|---|
| 米家控制与状态 | 上游 mijiaAPI CLI＋skill，CLI 装在 Hermes 容器持久化目录，经本地 terminal 调用 | 已支持主动刷新和规格查询；全屋状态通过现有命令或组合脚本完成，不另建每设备 MCP 工具 |
| Windows 控制 | AgentDock MCP（只开放 `exec_command`）＋ `windows-control` skill | 音量、媒体键、常用应用启停、锁屏、关屏、睡眠、关机倒计时；调用前经 Hermes 危险命令规则拦截；尚未实机验收 |
| 主动播报 | 上游 `mijiaAPI play` / 设备 action，直接走米家云端 | CLI 能力和 OH2P 目标已核对，实际听到播报、勿扰、离线及对话冲突仍待实机验收 |
| 定时 | Hermes cron | 实际可调用的 MCP / 插件工具、时区、任务持久化、取消与失败反馈 |
| Spotify | Hermes 官方 `spotify` 插件 | 7 组工具：播放、设备、队列、搜索、歌单、专辑、收藏；安装与重新授权后逐项验收 |
| 作品与曲目身份查询 | 现有网页搜索 / 阅读能力 + Spotify 元数据 | 作品版本、顺序、演唱者、录音版本与市场可用性 |
| 个人品味 | 收藏、歌单、近期播放；必要时补 top tracks / artists | 官方插件当前查到的定义未覆盖 top items；只在现有数据不足时补缺口 |
| 记忆 | Hermes 原生记忆 | 当前条目、写入条件、纠正与遗忘是否在新会话生效 |

不能承诺接入 Spotify 完整个性化推荐算法。Recommendations、Audio Features 等接口的可用性须按当前应用模式核实；Premium 不会解除开发模式接口限制。推荐可使用个人数据、搜索和艺人 / 专辑关联，理由要与实际取得的证据一致。

### 模型与运行参数

- 切换前核对配置为 `deepseek-v4.1-flash`、`reasoning_effort: none`、`max_turns: 6`。原日志中简单任务也会因反复 `tool_describe` 耗费 5～7 步。
- 已将 `agent.max_turns` 改为 15，同步 profile 源配置和运行配置并重启；配置加载器读回为 15。继续统计实际步数，避免只扩大上限。
- 检查 MCP / 插件工具如何加载，减少同一任务中重复读取工具说明。
- 用相同评测集比较当前模型与更强模型的正确率、时间、调用次数和费用；预算与可接受延迟待定，不直接更换模型。
- SOUL.md 保持精简：使用工具和记忆的方法、结果真实性、家规、必要澄清和回复风格。个人歌单别名与歌曲知识不作为固定提示词不断追加。

### 评测与验收

- 配置、工具接入和只读检查完成，不代表用户故事已验收；产品体验仍以用户反馈为准。
- 将 SP1～SP5、S2 / S4～S7、H1～H5 编成任务评测，另补约 30 条日常口令与表达变体；保留未出现在提示词和示例中的案例。
- 语义歌单验收包含首次与后续两次：初次无同名歌单时正确提出候选并等待确认；确认后由原生记忆保存，新会话中能复用。评测不预填别名，不以硬编码映射通过案例。
- 覆盖歌曲 / 歌单同名、翻唱、重复收藏、歌单改名或删除、权限不足、设备离线、部分数据读取失败和操作超时。
- 独立 session 隔离评测历史；需要记录工具调用、结果、任务时长、调用次数、澄清次数和虚报。`scripts/hermes_eval.py` 是拟新增能力，当前不可当作现成脚本。
- 先进行只读和模拟评测，再执行明确的真实验收指令。`HOME_TOOLS_DRY_RUN=1` 是拟支持的开关，现有代码不能假定支持；官方 Spotify 插件也不能假定自动识别它。
- 推荐单独记录用户的接受 / 跳过 / 纠正反馈。候选未收藏的结论须基于完整数据或明确说明检查范围。
- 最后在音箱与网页分别验收；云端控制额外验收 Windows 关机时的行为。

## 4. 技术规格

### 架构与职责

```text
音箱入口（bridge） / Hermes 网页
                 ↓
         Oracle：Hermes muse-home
          ├─ 记忆 / cron / 网页查询
          ├─ mijia-api skill → 本地 terminal → mijiaAPI CLI → 米家云 → 设备 / 音箱主动播报
          ├─ 官方 Spotify 插件 → Spotify Web API → 在线 Connect 设备
          └─ windows-control skill → AgentDock MCP（pre_tool_call 危险命令拦截）
                 → Cloudflare 隧道 → 用户 Windows 桌面会话中的 PowerShell

Grok Bot：由用户独立用于每周记忆核对
```

bridge 只负责音箱交互和与云端协议对接。Hermes 的个人数据、工具和任务不要求通过 bridge 才能工作。主动播报用米家云接口；与正在进行的语音对话发生冲突时先通过实机观察定位，再决定是否增加协调机制。

### 两种定时执行方式

当前安装版本已核对支持以下两种模式，均复用 Hermes 原生 cron，不另建调度系统：

| 模式 | 原生机制 | 适用场景与边界 |
|---|---|---|
| 固定动作，到点不调用 LLM | `no_agent=True` + `script`；CLI 为 `--no-agent --script` | 如“20 分钟后播放某首歌”。创建时解析并核对曲目 URI、设备和时间，到点执行。泛化方向为 Agent 生成脚本，调用 CLI 或已接通的插件接口。米家 CLI 已与 `no_agent` 脚本同在 Hermes 容器，脚本可直接调用；官方 Spotify 插件仍不能被脚本直接调用；未创建实际任务 |
| 到点启动 Agent | 普通 cron，任务保存自包含 prompt，可指定 `enabled_toolsets` | 如“每天北京时间 9 点搜索新闻并播报”。到点获取新信息、筛选总结，再调用播报工具；会产生模型调用 |

- 固定动作模式可在创建任务时使用 Agent 理解自然语言；`no_agent` 保证的是触发执行时不启动 LLM，不意味着创建任务也不需要理解。
- 一次性相对时间使用 `in 20m` 语义；不能用裸 `20m` 代替，否则可能被解释为重复间隔。周期任务明确指定时区。
- 已核对 gateway 与 ticker 正常运行，检查时没有活动任务。调度按周期扫描，不承诺秒级触发精度。
- 当前 cron 默认工具集为 `memory`、`spotify`、`terminal`、`skills`，已启用的 AgentDock MCP 按框架规则合并；旧米家 MCP 已停用，没有默认启用 `web`。新闻任务需要显式配置可用的网页工具，并通过上游 CLI 完成米家云播报的到点实测。
- 不因为普通 Agent cron 已可创建就宣称“新闻播报”或“固定工具定时”已验收；分别测试到点执行、取消、重启、设备离线和失败反馈。

### 固定动作的泛化方向：生成与执行脚本

用户希望固定动作定时可泛化，不为每种操作预写独立脚本。复用上游 CLI、Hermes 的脚本生成和 cron。用户已决定不为脚本另设隔离容器，脚本在 Hermes 容器内编写和运行。米家脚本可以直接调用 CLI，不再为其另建通用工具 RPC；Spotify 等插件若需从脚本调用，再根据实际需要核对接入方式。

期望流程：

1. 用户提出任务，Agent 在当前会话解析动作、对象和时间；需要找歌、确认歌单等交互在创建阶段完成。
2. Agent 在 Hermes 容器工作区编写 Python / shell，支持循环、条件和组合多个现有能力；米家直接调用上游 CLI。不得要求每个新场景先增加一份手写动作脚本。
3. 在相同执行环境中用模拟工具试跑，检查所用工具、参数、脚本输出与错误处理；模拟成功不能当作真实动作已完成。
4. 保存确定的脚本版本和任务参数，由 Hermes cron 的 `no_agent` 到点执行。到点运行已保存的脚本，不再调用模型生成或重写。
5. 支持查看、取消、修改时间和失败记录；更改动作逻辑时形成新脚本版本。需要到点获取新闻并总结等开放式推理时继续使用 Agent cron。

执行边界：

- 编写和到点执行都在 Hermes 容器，环境一致；脚本能接触该容器内的认证与持久化数据，这是用户接受的取舍。
- 未来需要从脚本调用官方 Spotify 插件时，再核对可用的调用方式。
- 脚本生成、依赖、工作区和定时执行入口需能跨会话及服务重启复用；实际动作不会因为试跑而提前执行。

已核对的原生能力与缺口：

- 当前已启用本地 terminal，支持保存和运行脚本；`file`、`code_execution` 等仍禁用，无须为普通 CLI 调用一并启用。
- 当前 `execute_code` 的 `hermes_tools` 白名单仅含 `web_search`、`web_extract`、文件操作和 `terminal`；不包含官方 Spotify 插件或米家 MCP，不能假设启用它后脚本就能直接调用这些工具。
- `no_agent` 的 `_run_job_script` 使用本地 `subprocess.Popen`，与本地 terminal 同在 Hermes 容器，因此米家 CLI 可直接用于无模型脚本；不再需要另接执行入口。
- 脚本自动发布流程尚未实现，未创建实际定时任务。

验收增加：由 Agent 生成未预写的工具组合脚本；试跑不产生真实播放 / 收藏；到点不调用 LLM；取消和重启后的任务状态正确。普通 Agent 新闻任务与脚本任务分别验收。

- **启动预热**：读取选定家庭的设备 / 房间和场景，缓存 ID、名称、型号、在线状态、更新时间；不要只默认取账号第一个家庭，明确当前家庭范围。先缓存列表，设备规格按需获取，避免启动时逐个请求所有属性。
- **主动刷新**：调用上游 `mijiaAPI -l --list_homes --list_scenes`；已部署的预热脚本可原子更新目录。用户说“我加了设备，重新看一下”时直接刷新，按真实列表报告变化；不另增自定义设备目录 MCP API。
- **按能力操作**：提供设备详情 / 属性 / 动作规格查询；读写范围、枚举、单位依据 MIoT 规格解释，传感器只读和红外设备走场景等差异来自真实能力。未取得规格时不能让模型猜 `on-2`、mode 数值或动作参数。
- **处理失配**：名称找不到时可刷新一次再匹配；同房间有多个同名设备时询问必要信息。临时断电 / 拔插只标记离线，不立即当作设备被删除；换绑或新设备的 ID 变化时不把旧定时任务静默指向新设备。
- **记忆分工**：设备事实表由目录工具维护，可提供精简摘要给 Agent；“书桌灯”“这个插座接电热毯”等用户确认的叫法和用途用 Hermes 原生记忆整理，不预填映射或另造一套记忆系统。记忆中的指代需在操作前与当前目录核对，不把历史在线状态或旧 ID 当作现状。
- **物理用途变化**：同一智能插座换插不同电器时，米家通常只看到原插座，无法自动感知所接负载。由用户明确用途变化并确认，更新原生记忆。
- **规则和发现分开**：保留明确的家庭范围和禁用设备 / 场景。它们是用户规则，不因刷新设备表而消失；普通设备无需逐个硬编码进可用列表。可编辑策略配置与设备目录分离，源码只保留通用执行逻辑。
- **失败处理**：刷新失败保留上一份有效目录并标明过期；不把错误响应解释为空家庭，不自动删除记忆或全部设备。需要实时状态时明确缓存时间。

历史基线的 `DEVICES`、`BY_DID` 和固定场景集合仍存在于回退文件中，但当前 Agent 已不使用；SOUL.md 设备表已移除。当前发现、刷新、规格与操作使用上游 CLI，设备角色使用原生记忆；明确禁用项另行保存。

验收覆盖 H4 / H5，以及无源码改动新增设备、改名、临时离线、换绑、同名设备、家庭范围、刷新失败和加热用途变化；刷新后的新设备能按规格操作，旧设备被移除后不会因残留记忆继续执行。

### 米家、定时与播报实现要求

- 已通过动态发现核对热水器用途与音箱身份；台灯仍待确认。当前链路不使用源码中的普通设备固定清单，SOUL.md 已改为通用查询说明，明确禁用项保留在独立家规配置。
- 即时播报复用现有米家动作；缺少适合的调用入口时才补专用工具。普通提醒遵守已确认勿扰策略，`urgent` 的例外尚未确定。
- cron 任务指令必须含设备、动作、时区和必要参数；新会话不能假设看到原对话。确认任务能持久化、取消并在重启后继续执行。
- 洗澡安排使用已确认的习惯与加热时长，回报具体时间；评测跨天、工作日与时间计算。若时间计算常失败，再补纯时间计算工具。
- 加热设备打开后可按用户要求安排提醒或关闭任务；手动关闭时取消相关任务。防忘关：电热毯由米家定时开关；热水器通电时由 Hermes 同时建定时关闭任务。Hermes 不再常驻观察器。
- 提醒和关闭使用持久化的 cron 任务，不以一次性进程内计时器代替。

### 授权、数据与 Windows 接口

- Spotify 修改歌单、读取收藏、近期记录和 top items 所需 scope 分别核对；新增 scope 需用户完成 OAuth 同意，刷新已有 token 不会自动扩权。
- 如果官方插件替换当前 Spotify MCP，应避免两组同名工具同时生效；确认设备选择、认证持久化和回退方式后再切换。
- 个人数据缓存记录更新时间；读取失败不能用空结果覆盖成功缓存，也不能将旧缓存冒充实时状态。
- 米家家规由 skill 和标准 CLI 调用校验承担，边界见部署说明。
- Windows 控制范围：系统音量、媒体键、常用应用（Spotify / Steam / 微信 / QQ）启停、锁屏、关显示器、睡眠，以及可取消的 60 秒关机倒计时。
- 原先“不给 Hermes 接入整机权限的 AgentDock 令牌”的约束已由用户改变：Hermes 获得 `exec_command`（完整管理员 PowerShell），以工具白名单、危险命令拦截钩子和 skill 规则约束；不开放 AgentDock 的文件、浏览器和管理类工具。

## 5. 风险与路线图

### 实施顺序

| 批次 | 交付 | 完成条件 |
|---|---|---|
| 0：事实与基线 | 核对设备、工具、授权、运行配置和评测方法；备份云端相关文件 | 真实设备身份明确，源配置与运行配置关系清楚，有当前行为记录 |
| 1：云端提醒 | 米家云端即时播报、cron 工具可见性、勿扰与错误反馈 | 音箱 / 网页能建任务，到点能播，Windows 关机不影响云端提醒 |
| 2：Spotify | 官方插件、必要授权、个人歌单、语义找歌、收藏、随机播放和初版推荐 | SP1～SP5 原话与泛化场景通过，推荐经过用户反馈；必要时补有限数据能力 |
| 3：习惯与米家 | 正确记忆、热水器 / 电热毯安排与取消、状态查询 | S2 / S4 / S6 / S7、H1 / H2 通过；每周核对仍由 Grok Bot 完成 |
| 4：整体调优 | 工具加载、轮数、模型对比及结果回报 | 固定评测结果可比较，费用与延迟有记录，达到已确认的上线门槛 |
| Windows | AgentDock 接入、危险命令拦截、`windows-control` skill（已部署） | 常用操作实机验收；拦截规则对删除类命令生效；不阻塞前面的云端能力 |

Spotify 与米家可按优先级交错实施；每批先验证现有能力，补缺口后再扩大范围。

### 风险与处理

| 风险 | 处理方式 |
|---|---|
| 语音转写和作品描述有歧义 | 先查事实，再匹配真实曲目；保留必要澄清，不能靠搜索排名确认身份 |
| Spotify API、授权、版权或设备能力限制 | 按当前应用和市场实测；结果如实反馈，新增授权与设备在线条件明确说明 |
| 官方插件不能覆盖全部用户故事 | 基于真实场景识别缺口，只补通用数据或工作流，避免重写完整播放器 |
| 多步推理成本与延迟上升 | 缓存个人数据、减少重复工具说明、确定性步骤集中处理，再评估模型与轮数 |
| cron 未取得工具、任务上下文不足或重启丢失兜底 | 明确工具可见性与完整任务参数，测试重启、取消、超时和部分失败 |
| 自动记忆污染与个人数据误归属 | 只存核实或确认的稳定信息，提供纠正 / 遗忘，不进行 Hermes 每周自动清理 |
| 云端播报打断正在进行的对话 | 先实测并记录具体冲突，确有需求再引入播放协调 |

### 待确认事项

1. 台灯等尚未识别的设备；音箱和热水器身份已核对，实际播报与控制仍待实机验收。
2. 设备勿扰与工具勿扰策略如何衔接，紧急提醒是否允许例外。
3. 官方插件的认证迁移方式，以及补收藏 / 编辑歌单等 scope 的授权步骤。
4. 加热提前量、提醒时间。习惯未知时由用户补充，不预填猜测。
5. 模型预算、可接受延迟，以及是否需要更强模型或按任务选模型。
6. 是否为 Windows 增加自定义受保护文件夹规则；是否需要口头确认后放行被拦截的操作。
