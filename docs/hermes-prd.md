# Hermes 家庭助手 PRD

> 适用部署：Oracle 上的 Hermes，profile `muse-home`。音箱（bridge）和 Hermes 网页聊天都是入口，能力要求相同。
> 状态：米家、Spotify、Windows、待办的基础接入已完成；米家读写与刷新已通过 API 端到端验收，其余用户故事待实机验收。最后更新：2026-10-20。

## 1. 目标

让助手理解自然描述，读取真实的个人数据和设备状态，完成操作并如实反馈。

原则：

- 能力优先用现成的官方 / 上游工具，确有缺口才补通用封装；不为单个设备、歌曲或叫法写规则。
- 提示词只写方法和行为边界，不堆设备表、歌曲表、动漫知识或个人同义词表。
- 个人叫法和习惯用 Hermes 原生记忆；定时用 Hermes cron；每周记忆核对由用户通过 Grok Bot 完成。
- 工具故障不写成用户偏好；没核实的事不说成已完成。

成功标准（待评测，不代表已达到）：

| 指标 | 目标与口径 |
|---|---|
| 米家任务完成率 | 固定评测集 ≥ 95%，含设备选择、动作、参数和结果回报 |
| Spotify 任务完成率 | 固定评测集 ≥ 90%，另报新描述、新歌单叫法的泛化结果 |
| 虚报成功 | 0 次；区分请求被接受、执行失败和状态已核实 |
| 记忆正确性 | 不把工具故障、公共同名歌单或未确认推断写成用户事实；纠正后新会话使用新值 |
| 步数与延迟 | 记录工具步数、重试、首个有效反馈和完成时间；绝对门槛待定 |

推荐是否合口味由用户判断；读取了收藏、候选真实存在、理由有据是前提，不能用模型自评代替。

## 2. 用户需求

### 用户与入口

同一位用户的家庭助手：在家通过缪斯音箱，或在 Hermes 网页聊天里控制米家、整理音乐、安排任务。云端米家控制与提醒不依赖 Windows 开机；Spotify 播放依赖在线的 Spotify Connect 设备，默认是用户的 Windows 电脑。

### Spotify

用户是 Spotify Premium 会员。以下是验收场景，不是只支持这些名字的规则。

| 编号 | 用户说法 | 预期行为 |
|---|---|---|
| SP1 | “我觉得《钢之炼金术士》新版的第二首 ED 很好听，你能帮我收藏吗？” | 查清作品版本、ED 顺序、歌名与演唱者，匹配正确录音，加入用户自己的 ACG 歌单；已有时不重复添加 |
| SP2 | “放我的 xx 歌单” | 优先找账号内真实的个人歌单，默认随机播放；明确要求按顺序时覆盖默认 |
| SP3 | “放二次元歌单” / “来点摇滚” | 没有同名个人歌单时，根据真实歌单推断候选并问“你是指这个吗”；确认后执行，由原生记忆保存叫法，后续直接复用 |
| SP4 | “根据我的品味推荐一首歌” | 实际读取收藏和歌单后选歌，必要时补近期播放；说明与已知口味的具体联系 |
| SP5 | 换作品、换 OP / ED、换译名、换歌单叫法，或追问“换一首”“把这首也加进去” | 结合真实数据和上下文处理没见过的表达；仍有关键歧义时只问必要的问题 |

验收细则：

- **歌曲身份**：不能直接收藏搜索结果第一条。区分原唱、翻唱、伴奏、现场、TV size / 完整版，默认优先原唱的正式完整录音（待验证的产品默认值）。版本影响意图又无法确定时询问。没有版权时如实说明，不偷偷用翻唱替代。
- **收藏目的地**：SP1 已明确归入 ACG，不再自动加入“喜欢的歌曲”。其他请求结合对话、歌单语义和已确认偏好决定；依据不足时不擅自分配。
- **个人歌单**：读取全部分页，区分自己的、可编辑的和仅关注的歌单；按真实 playlist ID 操作，改名后继续追踪，删除或失去权限时重新查找。
- **随机播放**：设置并核对随机状态，开播位置不要每次都是第一首；明确的顺序播放指令优先。核对实际播放设备和歌单；曲目短时间内没更新时不立即当成失败，也不在没核实时声称已经播对。
- **语义理解**：先找个人歌单里的准确匹配；没有时结合歌单名、描述、必要的曲目样本推断候选，确认后再执行。“二次元 → ACG”“摇滚 → rock”只是示例，不预先写入记忆、SOUL.md 或代码。
- **叫法学习**：确认后由 Hermes 原生记忆整理，后续复用，纠正时更新。不新增别名库、同义词规则或专门的记忆模块；只有原生能力在评测中确实不足时才调整通用说明。
- **推荐依据**：读取收藏 / 个人歌单，用有限样本和缓存减少重复读取。默认推荐收藏之外、本会话没推荐过、在 Spotify 可用的曲目；理由对应实际证据，数据不全时说明检查范围。
- **执行确认**：添加前去重，用真实 URI；超时等不确定结果先查当前状态再决定是否重试，避免重复添加。

### 米家、提醒与记忆

| 编号 | 场景 | 预期与验收 |
|---|---|---|
| S2 | “我今晚想洗澡” | 读取记忆中的入睡时间、洗澡与加热习惯，安排热水器提前开启并说清时间；缺少习惯或参数时询问，不编造 |
| S4 | “打开热水器 / 电热毯” | 执行后按需安排提醒；“洗完了 / 关掉”时关闭设备并取消对应任务。热水器通电时同时建一次性定时关闭任务（cron），手动关闭时取消；电热毯由用户在米家设定时开关 |
| S5 | “播放 Spotify / 打开 xx 软件” | Spotify 播放用官方插件；Windows 程序启停、音量、锁屏等经 AgentDock 与 `windows-control` skill |
| S6 | 不在家，从网页说“把空调关了” | 直接调用云端米家，Windows 关机时也能执行 |
| S7 | 长对话或新会话中控制设备 | 设备知识和稳定习惯仍然有效，不依赖早先对话是否还在上下文里 |
| H1 | “屋里几度 / 门关了吗” | 读取真实传感器，一次工具调用返回全屋状态，带采样时间，标出读不到的项 |
| H2 | “记住我工作日十一点半睡”后，新会话说“我今晚想洗澡” | 使用已确认习惯，不重复询问；“你记错了 / 忘掉……”能替换或删除记忆 |
| H3 | 定时提醒到点 | cron 实际调用米家云端播报，Windows 关机时也能播；区分云端已接受和确认已播完 |
| H4 | 新增 / 移除 / 改名设备后说“更新一下设备列表” | 从米家云刷新设备和场景并报告变化，新设备可直接查询和操作，不改代码和提示词；只是离线的设备保留身份并标离线 |
| H5 | “这个插座现在接的是电热毯，以后叫它电热毯” | 用户确认的叫法与用途由原生记忆保存；记了用途不等于该设备有自动关闭保护 |

通用体验：

- “亮一点 / 暗一点”做可解释的相对调整（默认 ±20%），“暖一点 / 白一点”调色温；属性和单位以设备规格为准。
- “我要睡了”“出门了 / 回来了”通过真实场景清单理解；“好冷 / 好热”只是表达感受时先确认要不要操作。
- 一句话多个动作时在同一任务里完成并分别核实；部分失败不能说成全部成功。
- 普通成功一句话回报；失败只说一次原因和可行的下一步；澄清要能区分候选，不反复确认明确的指令。
- 工具等待提示“稍等 / 我查一下”由音箱入口实现，云端不要重复播。

### 记忆分工

| 信息 | 存放与更新 |
|---|---|
| 设备 ID、家庭 / 房间、型号、能力、在线状态、场景 | 米家服务从云端发现并缓存，可主动刷新；属性和动作按设备规格读取。不写进 SOUL.md |
| 禁用设备 / 场景、默认播报音箱 | 家规配置 `house-policy.json`，由米家服务和 CLI 执行；刷新设备不会覆盖 |
| 稳定偏好、个人叫法、插座接的电器 | Hermes 原生记忆，用户明确表达或确认后保存；文档里的例子不预填 |
| 通用操作方法 | skill / 工具说明 |
| 工具缺陷、接口失败 | 运维记录，不写成用户偏好 |
| 每周记忆核对 | 用户通过 Grok Bot 完成；Hermes 不做周期核对或自动清理 |

记忆写入规则：

- 不从一次请求推断长期偏好；重复出现的偏好可以提出确认，但“多次出现”不能代替事实。
- 歌名、艺人和歌单身份以工具核实和用户确认为准；用户没纠正不能证明他拥有某个歌单或喜欢某艺人。
- 纠正时替换旧值，不留互相矛盾的记录；支持查询、纠正、遗忘。
- 记忆里的设备指代在操作前与当前目录核对，不把旧 ID 或历史在线状态当作现状。

### 范围边界

范围内：云端米家、Spotify、提醒、待办、记忆、模型行为、Windows 控制及其验收。Windows 控制在电脑关机或离线时不可用，它不是米家和提醒的前提。

范围外：音箱麦克风、KWS、AEC、灯效、TTS 和连续对话状态机归 bridge；不引入 Home Assistant；不重造 Hermes 的记忆和 cron；不为主动播报新增公网 bridge 通路。

## 3. AI 行为要求

### 决策流程

1. 解析意图和对话指代，识别缺少哪些事实或个人信息。
2. 从工具读取真实状态、个人数据和已确认记忆；涉及作品知识时搜索可靠资料。
3. 选择对象和参数；只有关键歧义无法消除时才问。
4. 用真实设备名 / ID、歌单 ID 或曲目 URI 执行，核实结果，处理部分失败。
5. 简短回报；符合记忆写入规则时才更新偏好。

分工：工具负责分页、去重、标识规范化、权限、校验、结果读回和缓存；模型负责理解自然描述、选择工具、综合事实和提出有针对性的澄清。

### 模型与运行参数

- 当前模型：Inception `mercury-3`（`reasoning_effort: low`）；`agent.max_turns: 15`；运行配置中 `tool_search` 关闭，工具直接暴露，不需要先 `tool_describe`。
- 用同一评测集比较模型的正确率、时间、调用次数和费用后再定是否更换；预算与可接受延迟待定。
- SOUL.md 保持精简：工具和记忆的用法、结果真实性、家规、必要澄清和回复风格。常用操作写明直接调用工具，减少先列目录、加载 skill 等多余步骤。

### 评测与验收

- 配置和工具接入完成不等于用户故事验收；产品体验以用户反馈为准。
- 把 SP1～SP5、S2 / S4～S7、H1～H5 编成任务评测，另补约 30 条日常口令和表达变体，保留不出现在提示词和示例里的案例。评测脚本待建。
- 语义歌单分两次验收：首次无同名歌单时提出候选并等待确认；确认后新会话能复用。不预填别名，不靠硬编码通过。
- 覆盖同名、翻唱、重复收藏、歌单改名或删除、权限不足、设备离线、部分读取失败和操作超时。
- 用独立 session 隔离评测，记录工具调用、结果、时长、调用次数、澄清次数和虚报。
- 先只读和模拟，再做真实操作。米家 MCP 支持 `HOME_TOOLS_DRY_RUN=1`（写操作只校验不执行）；Spotify 插件不支持模拟。
- 推荐单独记录用户的接受 / 跳过 / 纠正。
- 最后在音箱和网页分别验收；云端能力额外验收 Windows 关机时的行为。

## 4. 方案

### 架构

```text
音箱（bridge） / Hermes 网页
            ↓
     Oracle：Hermes muse-home
      ├─ 原生记忆 / cron / 网页搜索
      ├─ home_tools MCP → 宿主 mijia-service（127.0.0.1:9393，常驻缓存）→ 米家云 → 设备 / 音箱播报
      ├─ mijia-api skill → terminal → mijiaAPI CLI → 米家云（统计、耗材、no_agent 定时脚本）
      ├─ 官方 Spotify 插件 → Spotify Web API → 在线 Connect 设备
      ├─ 滴答清单官方 MCP（待办）
      ├─ caiyun-weather skill（天气）
      └─ windows-control skill → AgentDock MCP（pre_tool_call 危险命令拦截）
             → Cloudflare 隧道 → 用户 Windows 桌面会话的 PowerShell

Grok Bot：用户独立用于每周记忆核对
```

bridge 只负责音箱交互和协议对接；Hermes 的数据、工具和任务不依赖 bridge。主动播报直接走米家云；和正在进行的语音对话冲突时，先实测定位再决定是否加协调。

### 米家

日常控制走通用 `home_tools` MCP，背后是宿主常驻的 `mijia-service`（基于上游 mijiaAPI 库）；不常用功能走上游 CLI＋skill。部署见 [deploy/hermes-home-tools](../deploy/hermes-home-tools/README.md) 和 [deploy/hermes-mijia-cli](../deploy/hermes-mijia-cli/README.md)。

| 工具 | 用途 |
|---|---|
| `mijia_get(devices?, room?, props?)` | 读状态；不给设备就查全屋，一次批量请求，带采样时间 |
| `mijia_set(device, prop, value)` | 写属性；开关统一用 `on`，自动对应 `on-2` 等主开关 |
| `mijia_action(device, action, params?)` | 设备动作 |
| `mijia_scene(name)` | 运行场景 |
| `mijia_speak(text, speaker?)` | 音箱朗读，默认音箱见家规 |
| `mijia_devices(room?)` | 精简目录，平时不用先调 |
| `mijia_refresh()` | 重新从云端拉目录，返回新增 / 移除 / 改名 / 上下线 |

规则：

- **无设备表**：设备、属性、场景都来自米家云目录和 MIoT 规格，常驻缓存；目录不注入上下文。新增、改名、移除设备不改代码和提示词。
- **按名字直接调用**：模型传用户说的名字，服务端按 did → 完全一致 → 房间+名称 → 唯一子串匹配；多台命中返回候选；匹配不到先自动刷新一次。名字相近的候选只能用来问用户，不能自行替换设备。
- **按规格校验**：类型、范围、枚举在服务端检查；属性或动作名不对时返回可用列表，模型照着改一次。红外设备没有属性，提示改用操作它的场景。
- **结果分级**：`done`（云端确认）、`verified`（读回一致）、`accepted`（只确认收到，或场景 / 播报无法核实）、`failed`、`refused`。模型按状态回报。
- **刷新失败**保留上一份目录并标明更新时间；错误响应不当成空家庭，不自动删除记忆。临时离线只标离线；设备换绑 ID 变化时，旧定时任务不能静默指向新设备。
- **家规**：`house-policy.json` 由服务和 CLI 共用。禁止控制老家卧室树莓派（did `674635403`）；禁止 `关闭树莓派`、`树莓派开机`，以及任何实际会操作禁用设备的场景（目前包括回家、离家、晚安；要恢复，需在米家里把树莓派从场景中去掉）。默认播报音箱为 OH2P / Xiaomi 智能音箱 Pro（did `2181631827`），用户指定时按实际列表选择。可选 `homes` 限定管理的家庭。
- **不做常驻计时**：服务不自动关闭任何设备；提醒和定时关闭都用持久化的 cron 任务。
- **认证**：服务与容器内 CLI 共用 `/opt/data/.config/mijia-api/auth.json`。

已核对的设备事实：热水器是 did `2028616332` 的智能插座（主开关 `on-2`），原来接电热毯，现在接热水器（已存原生记忆）；家里有两台小爱音箱：OH2P `2181631827`、Play 增强版 `2121199409`。

### Spotify

- 使用 Hermes 官方 `spotify` 插件（7 组工具：播放、设备、队列、搜索、歌单、专辑、收藏），在 `api_server`、`cli`、`cron` 工具集启用。
- 已授权：播放读写、歌单读取与编辑、收藏读取与修改、最近播放。没有 top items 所需的 scope，不承诺这部分数据；需要时由用户重新完成 OAuth 同意（刷新 token 不会扩权）。
- 不能接入 Spotify 的完整个性化推荐。Recommendations、Audio Features 等接口按当前应用模式实测，Premium 不解除开发模式限制；推荐用个人数据、搜索和艺人 / 专辑关联。
- 音乐只在 Windows 电脑上播放；播放带记忆里电脑的 device_id。找不到设备时用 AgentDock 启动一次客户端，不反复重启。
- 自己的歌单用 `spotify_playlists` 列出后匹配，不用搜索找。个人数据缓存要记录更新时间，读取失败不能用空结果覆盖。

### Windows

- 复用用户电脑上的 AgentDock（登录后自启，运行在当前桌面会话，经 Cloudflare 隧道接入）。Hermes 只开放 `exec_command`，文件、浏览器、管理类工具不可见；令牌在 Hermes `.env`。
- 能力（`windows-control` skill）：音量（每次约 10%）、静音、媒体键、Spotify / Steam / 微信 / QQ 启停、锁屏、关屏、睡眠、可取消的关机倒计时（默认 60 秒）。禁止删改用户文件、装软件、改系统设置。
- 普通 exe 用 skill 里的启动模板（WMI `Win32_Process.Create`，工作目录设为 exe 所在文件夹，3 秒后读回进程和崩溃记录），商店应用用 `explorer.exe "shell:AppsFolder\<AppID>"`。AgentDock 在每条命令结束时会结束它派生的进程树，`Start-Process` 启动的 Win32 程序会跟着退出；`explorer.exe "xx.exe"` 的工作目录是 system32，按相对路径读数据的游戏会崩。
- 改变电脑状态的操作在同一条命令末尾读回结果，按读回回答；`exit_code: 0` 或 `status: running` 不算办成。
- 拦截：`pre_tool_call` 钩子 `agentdock_guard.py` 复用 Hermes 的危险命令规则（递归 / 强制删除、格式化、编码命令、`taskkill /f` 等），另拦截 `Start-Process` / `start` / `saps`（`-shutdown` 除外）和立即关机写法（`Win32Shutdown` / `Stop-Computer` / `Restart-Computer` / 不带倒计时的 `shutdown`）；命中或钩子出错都拦截。被拦截时按提示改正，需要用户本人操作的就告诉用户，不换写法绕过。
- 边界：命令文本匹配只防误操作，挡不住有意改写；电脑是内置 Administrator、UAC 关闭。用户接受这一取舍。

### 定时

复用 Hermes 原生 cron，两种模式：

| 模式 | 机制 | 适用 |
|---|---|---|
| 固定动作，到点不调用模型 | `no_agent` + `script` | 如“20 分钟后关热水器”。创建时由 Agent 理解并核对对象、参数和时间，到点运行已保存的脚本 |
| 到点启动 Agent | 普通 cron，保存自包含 prompt，可指定 `enabled_toolsets` | 如“每天九点搜新闻并播报”，到点需要获取新信息并总结 |

- 一次性相对时间用 `in 20m`，不能写裸 `20m`（会被当成重复间隔）；周期任务明确时区（Asia/Shanghai）。调度按周期扫描，不承诺秒级精度。
- 任务指令必须自带设备、动作、时区和必要参数，不能假设能看到原对话；支持查看、取消、修改时间和查看失败记录，重启后继续有效。
- cron 默认工具集：`memory`、`spotify`、`terminal`、`skills`，加上已启用的 MCP；新闻类任务需显式配置网页工具。
- 固定动作脚本的泛化方式：Agent 在 Hermes 容器工作区编写 Python / shell（可循环、条件、组合多个能力，米家直接调用 `/opt/data/.local/bin/mijiaAPI`），先用模拟方式试跑检查，再保存确定版本交给 `no_agent` 执行；改逻辑时形成新版本。不为每个场景预写动作脚本。试跑成功不等于真实动作已完成。
- 脚本和 CLI 同在 Hermes 容器，能接触容器内的认证数据，用户接受。官方 Spotify 插件目前不能从脚本直接调用，需要时再核对接入方式。

### 运维约束

- 配置有 profile 源配置（`~/hermes/profile`）和运行配置（`~/hermes/data`）两份，SOUL.md、config.yaml、MCP 源文件修改时两份同步。
- bridge 一次唤醒一个服务端会话（2026-10-21 起）：进入连续对话时生成新 ID，每轮带 `X-Hermes-Session-Id`、只发当前一句，Hermes 从 state.db 读回本次唤醒的历史（含工具结果和 skill 正文）；退出后丢掉，下次唤醒换新的。此前 bridge 自带纯文字历史，Hermes 对重复 `skill_view` 只回“内容未变”，模型拿不到 skill 正文。
- Hermes 对进行中的会话复用首轮存下的系统提示词；因为每次唤醒都是新会话，修改 SOUL / 记忆 / skill 后下次唤醒自动生效，不再需要 `hermes sessions repair-prompts`。
- `~/hermes`、`~/home-tools` 不是 Git 仓库，修改前先备份；仓库 `deploy/` 下保留部署副本和说明。
